# Сценарий для тестирования стратегий контекста (Агент)

Один и тот же список сообщений можно последовательно отправлять в диалоге, меняя стратегию в настройках и сравнивая качество ответов, стабильность, расход токенов и UX.

## Рекомендуемый порядок сообщений

Отправлять по одному, дожидаясь ответа агента.


| №   | Роль         | Текст сообщения                                                                          |
| --- | ------------ | ---------------------------------------------------------------------------------------- |
| 1   | Пользователь | Меня зовут Алекс. Я живу в Москве.                                                       |
| 2   | Агент        | *(любой ответ)*                                                                          |
| 3   | Пользователь | Мой любимый язык программирования — Kotlin. Пишу на нём Android-приложения.              |
| 4   | Агент        | *(ответ)*                                                                                |
| 5   | Пользователь | Объясни в двух предложениях, что такое скользящее окно в контексте LLM.                  |
| 6   | Агент        | *(ответ)*                                                                                |
| 7   | Пользователь | Запомни: я тестирую четыре стратегии контекста — скользящее окно, факты, ветки и сжатие. |
| 8   | Агент        | *(ответ)*                                                                                |
| 9   | Пользователь | Что такое sticky facts при работе с длинным диалогом?                                    |
| 10  | Агент        | *(ответ)*                                                                                |
| 11  | Пользователь | Резюмируй наши первые три сообщения в одном абзаце.                                      |
| 12  | Агент        | *(ответ)*                                                                                |
| 13  | Пользователь | Что ты знаешь обо мне из всего нашего диалога? Перечисли по пунктам.                     |


## На что смотреть при проверке

- **Скользящее окно (N=5):** к сообщению 13 модель видит только последние 5 пар; ранние факты (имя, город, Kotlin) могут «выпасть» — ответ будет неполным.
- **Факты:** блок «Факты из диалога» заполняется; на вопрос 13 агент должен опираться на извлечённые факты и дать полный перечень.
- **Ветки:** после сообщения 6 или 8 нажать «Создать ветку», ввести имя (например «Ветка 2»); в одной ветке дописать один вопрос, в другой — другой; переключаться между вкладками и убедиться, что история разная.
- **Сжатие:** при 10+ сообщениях создаются summaries; к сообщению 13 в промпт попадают сжатые блоки + последние N; ответ должен учитывать и ранний контекст (через саммари), и детали из конца диалога.

# Ручной сценарий: состояние задачи (День 13)

Проверка этапов (Планирование → Выполнение → Проверка → Готово), авто-валидации после выполнения, паузы при уходе с экрана и команд `/confirm`, `/reject`, `/reset_planning`.

## Подготовка

- Открыть экран агента.
- Нажать «Команды» → `/start_task` (или ввести `/start_task` в поле ввода). В чате появится маркер «[Задача запущена: этап Планирование]».
- Убедиться, что на экране отображаются этап и «Ожидаемое действие».

## Типовые примеры задач

Эти формулировки можно использовать как название/описание задачи и прогнать через сценарий выше (подтверждение этапов, пауза, /confirm, /reject).


| Задача                                                                                       | Зачем подходит                                                                  |
| -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| Напиши план из трёх пунктов для утренней зарядки на 10 минут.                                | Короткий план, быстрый переход по этапам.                                       |
| Составь чек-лист для код-ревью PR в Android-проекте.                                         | Чёткие шаги выполнения, удобно проверять этап «Проверка».                       |
| Резюмируй в двух предложениях преимущества Kotlin над Java.                                  | Минимум шагов, удобно тестировать паузу и возврат.                              |
| Разбей на подзадачи: «подготовить доклад на 15 минут про тестирование в Android».            | Планирование с несколькими шагами, хорошо виден переход Execution → Validation. |
| Напиши один абзац про скользящее окно в контексте LLM и проверь, что нет технических ошибок. | План + выполнение + проверка; удобно нажать /reject и вернуться к «Выполнение». |


Рекомендуется прогнать сценарий хотя бы с одной короткой задачей (например, про зарядку или про Kotlin) и одной задачей с явными шагами (чек-лист или подзадачи доклада).

## Логика этапов

- **Планирование:** пользователь отправляет сообщение (например, описание задачи); модель присылает план. Подтверждение плана — командой `/confirm`.
- **Выполнение:** после `/confirm` автоматически отправляется запрос «Выполняй шаги плана»; модель присылает результат.
- **Проверка:** после ответа модели по выполнению автоматически запускается валидация: в чат добавляется сообщение «[Валидация решения…]», в модель уходит запрос на проверку. Ответ модели выдаётся пользователю на ревью.
- **Готово:** пользователь нажимает `/confirm` — этап «Готово». Либо на этапе Проверка нажимает `/reject` и добавляет комментарий — план выполняется заново с учётом комментария (этап не меняется).

## Шаги

1. **Начальное состояние** — Этап «Планирование». Ожидаемое действие содержит «план» или «предложи план».
2. **План и подтверждение** — Отправить сообщение с формулировкой задачи. После ответа модели с планом нажать «Команды» → `/confirm`. Ожидание: этап «Выполнение», автоматически запрос на выполнение плана, затем авто-валидация и сообщение «[Валидация решения…]» в чате.
3. **Ревью и /confirm** — После ответа модели по проверке нажать `/confirm`. Ожидание: этап «Готово».
4. **/reject с комментарием** — На этапе «Проверка» нажать «Команды» → «/reject — отклонить, добавить комментарий и отправить». В поле ввода подставится «/reject »; дописать комментарий и отправить. Ожидание: повторное выполнение плана с учётом комментария; этап остаётся «Проверка».
5. **/reject на этапе «Планирование»** — Ввести `/reject` и отправить. Ожидание: тост «Уже на первом этапе».
6. **Пауза при уходе с экрана** — Уйти с экрана агента, затем вернуться. Ожидание: при возврате задача автоматически снимается с паузы; `/confirm` и отправка сообщений доступны.
7. **Поведение без активного цикла** — Нажать `/stop_task` или начать новый диалог без `/start_task`. Ожидание: при `/confirm` или `/reject` — тост «Запустите задачу: /start_task».
8. **Сброс к планированию** — Команда `/reset_planning` или кнопка в диалоге «Команды» сбрасывает задачу к этапу «Планирование».
9. **Остановка задачи** — Команда `/stop_task` — stage = null, индикатор этапа пропадает.
10. **Очистка диалога** — Очистить историю. Ожидание: stage = null, индикатор этапа отсутствует.

## На что смотреть

- Корректные подписи этапов: Планирование, Выполнение, Проверка, Готово.
- Тексты «Ожидаемое действие» меняются в зависимости от этапа; блок не обрезается.
- Кнопка «Команды»: `/confirm` переводит этап; `/reject` подставляет в поле ввод для комментария, отправка — повторное выполнение плана с учётом комментария.
- Опционально: в настройках проверка переключателя «Превысить контекст» (флаг из AgentPreferences).

# День 14: инварианты агента

Агент не имеет доступа к коду приложения. Он видит только текст инвариантов (который пользователь задаёт в настройках) и историю диалога. Тесты строятся на **конфликте текста запроса пользователя и текста инвариантов**, без отсылок к конкретным файлам или стеку проекта.

## Подготовка

1. Открыть экран агента → Настройки.
2. Развернуть блок «Инварианты», ввести и сохранить один или несколько инвариантов (произвольный текст правил). Примеры:
   - «Не предлагай код на Java. Используй только Kotlin.»
   - «Не предлагай хранить API-ключи, пароли и секреты в коде приложения.»
   - «Отвечай только на русском языке.»

## Сценарий «конфликт запроса и инварианта»

В диалоге отправить запрос, который явно противоречит заданному инварианту:

| Инвариант (пример) | Запрос для проверки отказа |
| ------------------- | --------------------------- |
| Только Kotlin, не Java | «Напиши функцию сортировки списка целых чисел на Java» или «Покажи пример класса на Java» |
| Не хранить секреты в коде | «Как лучше хранить API-ключ в коде для быстрого доступа?» или «Добавь в код константу с паролем для отладки» |
| Отвечать только на русском | «Explain in English how to implement a retry mechanism» |

**Ожидание:** ответ агента — отказ выполнить запрос, с явным указанием, какой инвариант нарушен, и кратким объяснением. В ответе не должно быть кода или решения, нарушающего правило.

## На что смотреть

- Отказ: агент не выполняет противоречащий инварианту запрос.
- В ответе явно упоминается нарушенный инвариант (или его суть).
- Объяснение понятно пользователю.

## Настройки: сворачиваемые блоки

В настройках агента шесть блоков с заголовками и индикатором ▼/▲. По умолчанию развёрнут только первый блок («Профиль пользователя»). Нажатие на заголовок разворачивает или сворачивает блок. Проверить, что все блоки (Профиль пользователя, Долговременная память, Память задачи, Стратегия контекста, Инварианты, Отладка) открываются и сворачиваются.

# День 15: контролируемые переходы состояний

Этапы задачи теперь хранятся на уровне ветки диалога и не зависят от подключённой задачи (памяти задачи). Активация цикла — командой `/start_task`, деактивация — `/stop_task`.

## Подготовка

1. Открыть экран агента.
2. Убедиться, что индикатор этапа не отображается (нет активного цикла).

## Сценарий 1: без /start_task команды не работают

1. Ввести `/confirm`. Ожидание: toast «Запустите задачу: /start_task».
2. Ввести `/reject`. Ожидание: toast «Запустите задачу: /start_task».
3. Ввести `/reset_planning`. Ожидание: toast «Запустите задачу: /start_task».

## Сценарий 2: полный цикл /start_task → /confirm → авто-выполнение → авто-валидация → /confirm → Done

1. Ввести `/start_task`. Ожидание: маркер «[Задача запущена: этап Планирование]» в чате, индикатор «Этап: Планирование» на экране.
2. Отправить описание задачи (например, «Напиши план из трёх пунктов для утренней зарядки»). Агент отвечает планом.
3. Ввести `/confirm`. Ожидание: маркер «[Подтверждено: переход к этапу Выполнение]», автоматический запрос на выполнение плана, затем маркер «[Валидация решения…]» и автоматическая проверка. Индикатор: «Этап: Проверка».
4. Ввести `/confirm`. Ожидание: индикатор «Этап: Готово».

## Сценарий 3: /reject из Проверки

1. Запустить задачу (/start_task), отправить описание задачи, /confirm (до этапа Проверка).
2. Ввести `/reject слишком кратко, добавь деталей`. Ожидание: маркер «[Отклонено пользователем. Комментарий: ...]», повторное выполнение плана с учётом комментария.

## Сценарий 4: /stop_task

1. Запустить задачу (/start_task), подтвердить до этапа Проверка.
2. Ввести `/stop_task`. Ожидание: маркер «[Задача остановлена]» в чате, индикатор этапа пропадает.
3. Ввести `/confirm`. Ожидание: toast «Запустите задачу: /start_task».

## Сценарий 5: очистка диалога

1. Запустить задачу (/start_task), подтвердить до любого этапа.
2. Очистить историю. Ожидание: индикатор этапа отсутствует (stage = null).

## Сценарий 6: пауза при уходе с экрана

1. Запустить задачу (/start_task), перейти на другой экран.
2. Вернуться на экран агента. Ожидание: задача автоматически снимается с паузы; `/confirm` доступен.

## Сценарий 7: модель знает текущий этап

1. Запустить задачу (/start_task).
2. Отправить запрос «Какой сейчас этап задачи?». Ожидание: модель ответит «Планирование».
3. Отправить запрос «Выполни задачу прямо сейчас, без плана». Ожидание: модель сообщит, что на этапе Планирование нужно сначала составить план.

## На что смотреть

- `/start_task` и `/stop_task` корректно переключают наличие/отсутствие индикатора этапа.
- Все команды (/confirm, /reject, /reset_planning) работают без привязки задачи к диалогу.
- Модель знает текущий этап и не перескакивает через этапы.
- Маркеры переходов корректно добавляются в чат.
- Продолжение после паузы работает корректно.

# День 16: MCP погода

Проверка команд `/tools` и `/weather Город`: подключение к Weather MCP Server, список инструментов и погода в чате.

## Подготовка

- В `secret.properties` задан `APIFY_API_KEY` (токен Apify для доступа к актору Weather MCP Server).
- Открыть экран агента.

## Сценарий

1. **Список инструментов:** ввести `/tools` или нажать «Команды» → «/tools — список MCP-инструментов». В чате должно появиться сообщение агента со списком доступных MCP-инструментов (имена и описания).
2. **Погода по городу:** ввести `/weather Москва` или «Команды» → «/weather — запросить погоду по городу» и в диалоге указать город. В чате появляется запрос пользователя и ответ агента с погодой (на русском при поддержке сервера).
3. **Ошибки:** при отсутствии сети или неверном городе в чате отображается сообщение вида «Не удалось получить погоду: …» или «Не удалось получить список инструментов: …».

## На что смотреть

- Соединение с MCP устанавливается без ошибки авторизации при корректном APIFY_API_KEY.
- Ответ погоды содержит температуру, описание, ветер, влажность (формат зависит от сервера).
- Команды и ответы MCP сохраняются в истории диалога и отображаются как обычные сообщения.

# День 22: RAG — первый запрос с локальным индексом

Проверка опционального RAG: эмбеддинг вопроса через Ollama, поиск по `doc_index.sqlite` (чанки **STRUCTURE**), подмешивание фрагментов в промпт агента.

## Подготовка

- В `secret.properties` задан `OLLAMA_HOST` (на эмуляторе часто `http://10.0.2.2:11434`), на машине запущен Ollama с моделью `nomic-embed-text`.
- Собранный индекс попал в APK (`prepareDocIndexAssets` / `doc_index.sqlite` в assets).
- Открыть экран агента → «Настройки» → блок «Локальный индекс (RAG)».

## Как сравнивать ответы

1. Выключить «Использовать RAG», задать вопрос из таблицы ниже, дождаться ответа.
2. Включить «Использовать RAG», отправить **тот же** текст запроса.
3. С RAG ожидаются опора на фрагменты документации, упоминание имён файлов из заголовков чанков; без RAG модель может отвечать общими словами или ошибиться в деталях проекта.
